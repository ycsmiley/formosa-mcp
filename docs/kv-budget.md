# Account-wide KV write budget (p35-r1fix2)

Cloudflare KV Free's 1,000 writes/day are shared by **all writers and Workers in the account**. The table audits the schedules in this repository; it is a planning envelope, not measured production usage or an account-wide reservation. Additional applications, manual runs and retries outside these workflows consume additional allowance. Rate-limit Durable Objects and the TDX gateway's SQLite storage are **not KV**.

## Scheduled writers

“Typical” assumes a healthy weekday with one daily stock revision, no invoice revision, unchanged outage notices and garbage content outside renewal day, 70 populated garbage districts, warm rail stations/timetables, and healthy Worker disaster collection. “Worst” allows all scheduled writers to change on the same day: a weekday 25th of an odd month with storms. Counts include indexes, stock validators and rail usage records. See the qualifications below before treating these as ceilings.

Rail writes its usage record **before every HTTP call**, including token acquisition, retries and failed calls. A cold run has six snapshots and, with three TRA pages per date, ten data calls plus a token: 17 writes without retries. The table allows 20 usage writes plus six snapshots per run: default `intervalMs=60_000` spaces calls, and the workflow's **20-minute job timeout** prevents more than 20 calls. Setup and HTTP time generally lower that bound. Without this workflow timeout, the code can make up to 40 calls (ten data gets × two attempts × token/data when tokens expire between requests) plus six snapshot writes per run: 92/day and a combined **745/day**. The default 300-call monthly snapshot reserve also limits HTTP usage but is not a per-day quota. Manual interval/quota overrides are outside this table.

\* Garbage now reuses the previous city's generation when all district hashes are unchanged. It reads each existing shard and skips identical values, repairs missing/corrupt values individually, and renews all shards of the city only when its last full write is **older than seven days** (14-day TTL). Optional city `writtenAt` tracks that full write, falling back to legacy `fetchedAt`. Repairs do not advance the full-write timestamp. The index writes once per run when any city is successfully checked, persisting its `checkedAt` even when no shard changes. Optional `indexWrites: { day, count }` enforces a default cap of **3 index writes per UTC day**, including manual runs (`maxIndexWritesPerDay` can override it); the scheduled run uses **1/day**. Once capped, collection returns before fetching or writing shards; a new UTC day resets the count. Legacy indexes without the counter remain readable. The cap assumes serialized runs and successful index persistence. A changed district creates a new generation and rewrites **all districts of that city**, preserving other cities. Publication failures keep the old generation readable. The typical unchanged, nonrenewal day costs **1** garbage write; with daily polling and strict >7-day renewal, synchronized renewals cost 71 every eight days plus one index on each of the other seven days, averaging **9.75/day**. Across other scheduled writers, that gives **48–50/day** on nonrenewal days, **118–120** on synchronized renewal days, or approximately **56.8–58.8/day** amortized (add 1 for a usual invoice revision). The all-change/renewal worst case remains **71** garbage and **705** total. The 71 assumes 29 New Taipei + 12 Taipei + 29 Taichung populated districts. District names are not allowlisted, so malformed/new upstream names can exceed this planning count; it is not a code-enforced cap. `fetchedAt` retains its snapshot publication semantics; freshness uses `checkedAt`, falling back to `fetchedAt` for legacy indexes. Outages allow all 22 recognized counties per source (3 × 22 = 66), even though expected Taipei-water coverage is much smaller and Taiwan Water currently returns no usable export.

**The combined scheduled envelope is approximately 700/day (705).** The reviewer's no-retry rail estimate (34/day) gives **562 non-disaster + 125 disaster = 687/day**; allowing workflow-bounded rail retries gives **580 + 125 = 705/day**. This is below 1,000 for the stated schedules and geographic assumptions, leaving 295/day for other account writers. It is five writes above a strict 700 target. Adding `--max-calls 18` to the rail workflow command would allow at most 18 usage writes + six snapshots per run, reducing rail's scheduled worst from 52 to 48/day and the combined total to **701/day**, independent of the job-timeout assumption. A strict ≤700 envelope would require `--max-calls 17`: 46 rail writes/day and **699/day** combined. Normal cold collection needs at most eleven calls, leaving six for retries at that cap. **Garbage steady-state writes and schedules are unchanged; disaster degradation recording adds one overdraft write per writer to the rolling-24h envelope.** A shared account-wide coordinator remains necessary for a strict account-wide guarantee.

## Disaster publication policy

Both writers publish indexes only for changes to `ok`, `closed`, `sha`, `reason`, `empty` or `skipped`, or a heartbeat after **55 minutes**. Heartbeats anchor to run start, yielding roughly 60–70 minutes on these schedules, inside the 90-minute reader freshness window. GHA suppresses heartbeat-only publications when every selected source is skipped; an unchanged healthy-Worker skip writes nothing. Source/fetch times can therefore advance in memory without advancing KV on each poll. Before discarding an otherwise unchanged selected, non-skipped failure/closed attempt, re-read the writer index and, if merging changes its `ok`/`closed` state, publish the merged index alone under the same must-record budget/overdraft rules; missing, corrupt or unreadable rechecks and unchanged merged status write nothing.

Immutable shards retain eight-day TTLs. A changed sha writes a shard; an unchanged shard renews after three days **only alongside an index publication already due**. Shards precede the writer's independent index. Failed publication retains that source's previous reference.

Each KV writer persists `budget: { tokens, at }` in its own index. At publication, `tokens = min(burst, previousTokens + perHour × elapsedHours)`. Each planned shard and the one index cost a token. Worker uses **3/hour, burst 9** (9 + 24×3 + 1 overdraft = **82 writes per rolling 24 hours**); GHA uses **1.5/hour, burst 6** (6 + 24×1.5 + 1 = **43**), totaling **125** disaster writes. These conservative limits include the initial burst and manual invocations sharing the persisted index. Ordinary success/heartbeat publications require sufficient tokens. When success shards do not fit, DGPA shard + index takes priority; dropped success shards restore only that source's stored state. Failures and login-required (closed) states from this run are never replaced with previous successes to make room for DGPA.

A selected, non-skipped source with `ok: false` and a change in `ok`/`closed` is **must-record**. If necessary, drop all new success shards and publish the failure index alone: this may overdraw only when pre-charge tokens are nonnegative, persisting no less than **-1**. The charge is recorded without resetting other budget state. If tokens are already negative and a new transition cannot be recorded, publish nothing, warn and return `exitCode=1`; a stored success with such an exhausted overdraft is inconsistent with a prior successfully stored must-record transition. Local directory/stdio stores have no bucket.

Before writing any shard, re-read the writer index. If its budget timestamp is later than the initial budget, use the minimum refilled token balance and re-apply shard priority, shortfall and must-record overdraft rules. Insufficient budget therefore stops publication before any shard write begins.

Immediately before index publication, re-read the writer index again and merge each source against both the pre-shard and final observations in two parts, retaining the maximum heartbeat. Attempt status (`ok`, `closed`, `skipped`, `reason`, `fetchedAt`) follows the later `fetchedAt`; success evidence (`sha`, `sourceUpdatedAt`, `lastSuccessAt`, `count`, `writtenAt`, `empty`) follows the newer `sourceUpdatedAt`, breaking ties by later `lastSuccessAt`, then by `fetchedAt` only for states that are themselves `ok`. A later failure therefore preserves concurrent newer success evidence while still warning readers that the latest fetch failed. A successful attempt uses its whole state only when its evidence wins; otherwise keep the evidence winner's whole state, so a slow older success cannot regress the stored shard or source timestamp. Publish when the merged source states differ or a heartbeat is due. Only a run with no shard attempts may skip a superseded index publication. Every run that attempted a shard write publishes the merged index and charges all shard attempts plus one index, even when none of its source states wins. Use the minimum refilled balance across the initial budget and all observed budgets dated later than it, preserving the latest budget timestamp; persisted tokens are clamped at **-1**. Stale final replicas, or missing, corrupt or unreadable re-reads, retain previously observed publication state.

The bucket assumes serialized publications for each writer and successful persistence of the writer index. The two re-reads prevent observed stale overwrites and reuse observed concurrent budget charges, but KV is eventually consistent and has no compare-and-swap. Overlapping same-writer runs can still exceed the bucket by at most the writes already in flight; clamping the recorded balance at -1 bounds the stored overdraft, not that residual non-transactional overspend. A lost index write after shard attempts can also lose their charge. A same-writer version written after the final re-read and before the put can still be overwritten (e.g. 03:00 regresses to 02:00); this accepted rare window requires overlapping same-writer runs, while GHA workflow concurrency serializes its runs and Worker crons are 10 minutes apart with deadlines. The index can lag by at most one version until the next collection (≤ ~10 minutes for Worker / next GHA run), so readers see the previous version's timestamps and the stale/failed-attempt guards still apply. By decision, no lock or Durable Object is added; production Worker overlap/failure behavior still needs profiling. Failed shard writes are charged conservatively in the next successful index.
